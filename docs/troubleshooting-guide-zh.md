## 安装和设置问题

### 找不到框架文件

**症状：**
- AI 不识别 CursorRIPER 命令
- 关于缺少框架文件的错误消息
- AI 在回复中不确认框架

**可能原因：**
- 文件未复制到正确位置
- 文件名称或扩展名不正确
- Cursor 不识别框架文件

**解决方案：**
1. 验证文件是否存在于 `.cursor/rules/` 目录中
2. 确保所有框架文件都具有 `.mdc` 扩展名（而不是 `.md`）
3. 检查文件权限
4. 重新启动 Cursor IDE 以重新加载框架文件

### 框架未初始化

**症状：**
- `/start` 命令不触发 START 阶段
- 没有框架初始化的确认

**可能原因：**
- 核心文件丢失或损坏
- 文件路径不正确
- 与其他 Cursor 规则冲突

**解决方案：**
1. 验证 core.mdc 和 state.mdc 是否存在并格式正确
2. 检查控制台是否有错误消息
3. 尝试手动将 state.mdc 设置为 `PROJECT_PHASE: "UNINITIATED"`
4. 从源代码重新安装框架文件

## 文件扩展名问题

### GitHub 仓库与项目文件

**重要提示：** 在 GitHub 仓库中，框架文件使用 `.md` 扩展名以便在 GitHub 上正确渲染。在项目中实施时，这些文件必须重命名为使用 `.mdc` 扩展名。

**症状：**
- 框架无法正确加载
- AI 不识别框架命令
- AI 回复中没有模式声明

**解决方案：**
1. 从 GitHub 下载框架文件
2. 将所有框架规则文件从 `.md` 重命名为 `.mdc`：
   ```bash
   # Linux/macOS
   cd .cursor/rules/
   for file in *.md; do mv "$file" "${file%.md}.mdc"; done
   
   # Windows PowerShell
   Get-ChildItem -Path ".cursor\rules" -Filter "*.md" | Rename-Item -NewName { $_.Name -replace '.md','.mdc' }
   ```
3. 保留 `memory-bank/` 目录中的文件使用 `.md` 扩展名
4. 重新启动 Cursor IDE

### 要重命名的文件

这些文件必须从 `.md` 重命名为 `.mdc`：
- `core.md` → `core.mdc`
- `state.md` → `state.mdc`
- `start-phase.md` → `start-phase.mdc`
- `riper-workflow.md` → `riper-workflow.mdc`
- `customization.md` → `customization.mdc`

## 状态管理问题

### 不正确的模式或阶段

**症状：**
- AI 使用错误的模式声明
- 命令不触发模式更改
- 会话之间的行为不一致

**可能原因：**
- 损坏的 state.mdc 文件
- 不完整的模式转换
- 文件保存问题

**解决方案：**
1. 检查 state.mdc 文件以查看当前值
2. 手动更新状态值为正确设置：
   ```
   PROJECT_PHASE: "DEVELOPMENT"
   RIPER_CURRENT_MODE: "RESEARCH"
   ```
3. 重置框架状态：
   ```
   请将框架状态重置为 DEVELOPMENT 阶段和 RESEARCH 模式。
   ```

### 重新初始化问题

**症状：**
- 无法重新启动项目
- 在之前初始化后不识别 "/start" 命令
- 关于重新初始化的错误消息

**可能原因：**
- 框架防止意外重新初始化
- 损坏的状态文件
- 缺少确认

**解决方案：**
1. 使用明确的重新初始化确认：
   ```
   /start
   CONFIRM RE-INITIALIZATION
   ```
2. 如果仍然失败，手动编辑 state.mdc：
   ```
   PROJECT_PHASE: "UNINITIATED"
   START_PHASE_STATUS: "NOT_STARTED"
   ```
3. 如果需要，删除并重新安装框架文件

## 内存库问题

### 缺失或损坏的内存文件

**症状：**
- AI 缺乏项目上下文
- 关于缺失内存文件的错误消息
- 不完整或无意义的回复

**可能原因：**
- 文件被删除或移动
- 不当更新损坏文件
- 权限问题阻止保存

**解决方案：**
1. 检查内存库目录中是否存在文件
2. 如果可用，从备份恢复：
   ```
   memory-bank/backups/[date]/
   ```
3. 如果没有备份，请求 AI 重新创建基本内存文件：
   ```
   请根据我们当前的项目状态重新创建缺失的内存库文件。
   ```

### 不一致信息

**症状：**
- AI 给出矛盾的回复
- 引用过时或不正确的信息
- 对项目需求或状态的混淆

**可能原因：**
- 内存文件更新不一致
- 多个团队成员进行不协调的更改
- 带有格式错误的手动编辑

**解决方案：**
1. 检查所有内存文件的一致性
2. 更新所有文件中的时间戳和版本
3. 请求 AI 调和不一致之处：
   ```
   请审查所有内存文件并调和项目信息中的任何不一致之处。
   ```
4. 对于严重问题，考虑完全刷新内存库

## 工作流中断

### 模式约束未被遵循

**症状：**
- AI 在研究模式下提出建议
- 在计划模式下实施代码
- 在执行模式下不遵循已批准的计划

**可能原因：**
- 模式未正确声明
- 状态文件不一致
- AI 上下文限制

**解决方案：**
1. 明确强化模式约束：
   ```
   您处于研究模式。请仅收集信息和提问。
   ```
2. 重启聊天会话以刷新 AI 上下文
3. 验证 state.mdc 显示正确模式
4. 如果可用，使用 Cursor 的自定义模式（参见 custom-modes-guide.md）

### 计划模式检查表问题

**症状：**
- 未生成检查表
- 检查表项目不完整或模糊
- 检查表未反映完整实施需求

**可能原因：**
- 提供的信息不足
- 复杂要求未充分阐明
- AI 上下文限制

**解决方案：**
1. 明确请求详细检查表：
   ```
   请生成一个全面的、编号的实施检查表，包含具体、可操作的步骤。
   ```
2. 提供更详细的需求
3. 将复杂功能分解为更小的组件
4. 在 customization.mdc 中调整 PLAN_QUESTION_COUNT

### 执行模式实施问题

**症状：**
- AI 偏离已批准的计划
- 实施不完整
- 实施过程中出错

**可能原因：**
- 计划不够详细
- 未预料到技术挑战
- 计划步骤中的模糊性

**解决方案：**
1. 如果需要偏离，返回计划模式：
   ```
   /plan
   我们需要修改计划以处理这个意外问题。
   ```
2. 创建更详细的实施检查表
3. 遇到问题时更新 progress.md
4. 将复杂实施分解为更小的步骤
